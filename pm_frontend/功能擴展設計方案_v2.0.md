## 一、需求來源分析

### 1.1 流程圖解讀（圖一：工程師工作日誌與工作指派流程）

圖一描述了工程師日常工作的完整分類體系和管理鏈路：

**工程師每日工作分類：**

| 分類 | 說明 | 對應系統模塊 |
|------|------|-------------|
| 進行專案項目 | 已立案的正式專案工作 | ✅ 已有：專案管理 |
| CR / AR | 變更請求/異常報告，屬於專案衍生需求 | ⚠️ 部分覆蓋：可歸入專案功能任務，但缺少 CR/AR 專門分類標記 |
| 教育訓練 / OJT | 培訓學習時間 | ❌ 缺失：無工作分類記錄 |
| 週會 / 月會 | 會議時間消耗 | ❌ 缺失：無工作分類記錄 |
| Others | 其他雜項工作 | ❌ 缺失：無工作分類記錄 |

**專案工作階段（WBS 展開）：**

| 階段 | 子項 | 系統對應 |
|------|------|---------|
| 專案/CR/AR 需求 | 系統規格書 | 功能任務分組可覆蓋 |
| 系統開發 | 系統開發項目 | ✅ 功能任務 |
| 系統測試 | Code Review、整合測試 | ✅ 功能任務（測試工程師） |
| 系統上線 | 使用者測試、上線後觀察 | ✅ 功能任務（運維） |

**右側工作指派體系：**
- 系統分析 → 專案需求 → WBS → 功能任務
- 修改需求書 → CR/AR
- 臨時任務指派

**關鍵管理訴求（圖底文字）：**
> 可以看到專案整體進度，進度是否有 Delay。如果有 Delay 就需要進行報告以及提供 Backup Plan。

### 1.2 IT QCDST Dashboard 解讀（圖二、圖三）

圖二展示了 QCDST Dashboard 的設計理念，包含四大核心價值：KPI 控管、集中管理、資訊整合、分層列管。

圖三是實際的 Dashboard 界面，展示了 QCDST 六大維度：

| 維度 | 英文 | KPI 舉例 |
|------|------|---------|
| Quality（品質） | Q | SOX/QA/客戶/稽核缺失件數、A類/B類異常件數 |
| Cost（成本） | C | CR ROI |
| Delivery（交付） | D | Project OTD（準時交付率）、CR OTD |
| Service（服務） | S | CR 平均滿意度、myASE Portal 響應時間 |
| Technology（技術） | T | PET+M 實作件數 |
| Management（管理） | M | 人員離職率、SA&D-UML 認證合格率 |

**Dashboard 四大功能模塊：**
1. **個人化 Dashboard**：一階總覽 QCDSTM，二階展開細節
2. **KPI 設定及控管**：列管 KPI 指標、系統指標、自訂指標
3. **週檢視/月檢視**：提供不同時間維度的檢視
4. **警示機制**：系統自動計算並警示未達標 KPI

### 1.3 用戶明確提出的需求

1. **個人工作日誌導出**：匯出日誌並進行統計彙整
2. **專案工時分佈**：每個專案花了多少時間，圓餅圖展示
3. **BU/單位維度統計**：工時花在哪個 BU 或單位
4. **正常/加班時間區分**：統計加班時數，正常與加班要註明
5. **作業內容清楚描述**：日誌需完整記錄工作內容
6. **日報提醒告警**：每日提醒填寫日報，避免忘記
7. **工時充足性檢查**：計算每人每天工時是否足夠
8. **管理異常聚焦**：著重管理異常，正常則減少管理時間

## 三、新增功能詳細設計

### 3.1 個人工作日誌（DailyLog）—— N1 核心功能

#### 3.1.1 設計理念

工作日誌是整個工時統計體系的**數據源頭**。工程師每日記錄當天的工作內容，系統自動彙整為個人/團隊/專案維度的統計數據。

#### 3.1.2 數據模型

```
工作日誌 (DailyLog)
├── log_id          PK
├── work_no         記錄人工號
├── log_date        日期（yyyy-MM-dd）
├── entries[]       日誌條目列表
│    ├── entry_id       PK
│    ├── work_category  工作分類（見 3.2）
│    ├── project_id?    關聯專案（可選，非專案工作留空）
│    ├── function_id?   關聯功能任務（可選）
│    ├── duty_id?       關聯臨時任務（可選）
│    ├── bu_unit?       關聯 BU / 單位（如：製造部、品保部）
│    ├── description    工作內容描述（必填，≥10字）
│    ├── hours          耗時（小時，支持 0.5 精度）
│    ├── is_overtime    是否加班（boolean）
│    ├── overtime_hours 加班時數（當 is_overtime=true 時）
│    └── files[]        附件列表
├── total_hours     當日總工時（自動加總）
├── overtime_hours  當日加班工時（自動加總）
├── status          draft（草稿）| submitted（已提交）| confirmed（已確認）
├── submitted_at    提交時間
└── confirmed_by?   確認人（直屬主管）
```

### 3.2 工作分類體系 —— N2

#### 3.2.1 分類定義

| 分類 Code | 顯示名稱 | 顏色 | 是否關聯專案 | 說明 |
|-----------|---------|------|-------------|------|
| `project` | 專案工作 | 🔵 藍 | ✅ 必選 | 正式專案的功能開發、測試、部署等 |
| `cr_ar` | CR / AR | 🟢 綠 | ✅ 必選 | 變更請求/異常報告處理 |
| `training` | 教育訓練 / OJT | 🟡 黃 | ❌ | 內部培訓、外部課程、技術分享 |
| `meeting` | 週會 / 月會 | 🔴 紅 | ❌ | 例行會議、專案會議、跨部門會議 |
| `duty` | 臨時任務 | 🟣 紫 | 條件選 | 系統中的臨時任務 |
| `other` | 其他 | ⚪ 灰 | ❌ | 無法歸類的工作事項 |

#### 3.2.2 功能任務擴展（A3）

`ProjectFunction` 表增加 `task_type` 字段：

```typescript
type TaskType = 'requirement' | 'development' | 'cr_ar' | 'testing' | 'deployment' | 'other'
```

用於在統計報表中區分專案內不同類型的工作。

### 3.3 正常/加班工時區分 —— N3

#### 3.3.1 標準工時定義

| 參數 | 默認值 | 說明 |
|------|--------|------|
| 每日標準工時 | 8.0h | 超過部分視為加班 |
| 每週標準工時 | 40.0h | 週統計基準 |
| 工作日 | 週一至週五 | 週六日的工時全部視為加班 |

> 這些參數應可在系統管理中配置。

#### 3.3.2 加班判定邏輯

1. 日誌條目手動標記 `is_overtime = true` → 明確加班
2. 當日總工時 > 標準工時 → 超出部分建議標記為加班（系統提示）
3. 週六/週日的工時條目 → 自動標記為加班
4. 主管可在確認日報時調整加班認定

#### 3.3.3 加班統計展示

在 StatisticsPage 新增加班相關圖表：
- **月度加班趨勢折線圖**：各成員月加班時數趨勢
- **加班工時佔比環形圖**：正常 vs 加班比例
- **加班排行榜**：按加班時數降序排列

### 3.6 工時充足性檢查 —— N6

#### 3.6.1 檢查邏輯

| 指標 | 計算方式 | 閾值 | 狀態 |
|------|---------|------|------|
| 日工時充足率 | 當日實際工時 / 標準工時 | ≥ 100% ✅ 正常 | < 75% 🔴 不足 |
| 週工時充足率 | 本週累計工時 / (已過工作日 × 標準工時) | ≥ 95% ✅ 正常 | < 80% 🔴 不足 |
| 月工時充足率 | 本月累計工時 / (已過工作日 × 標準工時) | ≥ 90% ✅ 正常 | < 80% 🔴 不足 |

#### 3.6.2 主管異常報表

當成員工時充足率低於閾值時，自動納入異常管理報表，主管可查看：
- 誰的工時不足（可能是未填日報或確實工時不夠）
- 趨勢是否在惡化

### 3.7 異常管理看板 —— N7

#### 3.7.1 設計理念

> 著重於管理異常，正常則可以減少時間管理

## 九、總結

本次擴展的核心是建立**工作日誌體系**作為數據源頭，在此基礎上實現：

1. **向下**：工程師每日記錄工作內容，系統自動計算工時統計
2. **向上**：主管通過圓餅圖、堆疊柱狀圖等了解人力分佈和加班情況
3. **橫向**：異常管理看板自動篩出需要關注的問題，讓主管把精力放在異常管理上

設計原則始終圍繞用戶提出的管理目的：**著重於管理異常，正常則可以減少時間管理**。
